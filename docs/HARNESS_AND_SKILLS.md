# LLM 하네스와 스킬: 왜 필요한가

최종 갱신: 2026-10-06

## 한 문장 결론

LLM은 **생각을 제안하는 두뇌**, 하네스는 그 두뇌가 컴퓨터를 안전하게 보고 움직이고 확인하게 하는
**몸과 작업 규칙**, 스킬은 자주 하는 일을 다시 배우지 않도록 저장한 **검증된 작업 설명서**다.

좋은 개인 PC 에이전트는 말을 길게 잘하는 시스템이 아니라, 사용자가 허용한 범위에서 요청한 결과를
만들고 그 결과가 실제로 생겼는지 다른 방법으로 확인하는 시스템이다.

## 유치원생에게 설명하면

로봇에게 “내 장난감을 상자에 넣어 줘”라고 말했다고 생각하자.

- **LLM**은 “장난감을 들어서 상자에 넣으면 되겠네”라고 생각하는 로봇의 머리다.
- **도구**는 로봇의 눈과 손이다.
- **하네스**는 “먼저 어느 장난감인지 보고, 허락받고, 한 개만 들고, 상자에 들어갔는지 다시 보자”라고
  정한 로봇의 몸과 안전 규칙이다.
- **스킬**은 “장난감 정리하는 법” 그림 카드다. 다음번에는 처음부터 다시 고민하지 않고 카드를 보고
  빠르고 같은 방법으로 정리한다.
- **검증기**는 마지막에 상자를 다시 보는 선생님이다.

로봇이 “잘 정리했어요”라고 길게 말해도 장난감이 바닥에 있으면 실패다. 그래서 생각 과정의 길이보다
**상자 안에 실제로 들어갔는지**가 더 중요하다.

## 용어를 정확히 나누기

| 구성요소 | 하는 일 | JARVIS-PC의 예 |
|---|---|---|
| 모델(LLM) | 언어 이해, 후보 계획 생성 | NVIDIA NIM의 GLM 계열 모델 |
| 도구 | 외부 상태를 읽거나 바꿈 | Native API, UIA, 제한된 PowerShell, 브라우저·Explorer adapter |
| 하네스(scaffold/runtime) | 모델 호출, context, 도구 선택, 반복, 승인, 오류 처리, 상태 관리를 엮음 | Intent Gate → Planner → Policy → Executor → Verifier → Audit |
| 스킬 | 특정 목표를 수행하는 재사용 가능한 절차와 자료 | 이번에 만든 `outcome-driven-local-work` |
| 정책 | 해도 되는 행동인지 판정 | GREEN/YELLOW/RED, target identity, 승인 토큰 |
| 검증기 | 실행자의 말과 독립적으로 최종 상태를 확인 | 파일 hash/readback, PID/HWND, OS volume readback, memory 재검색 |
| 평가 하네스 | 같은 조건에서 성공률·비용·안전을 재는 시험장 | B0/B1/P1/P2, exact-grid benchmark, snapshot VM |

“하네스”는 모델 가중치 바깥의 실행 환경 전체를 가리키는 실무 용어다. 같은 모델이라도 어떤 context를
보여 주는지, 어떤 도구를 어떤 형식으로 주는지, 실패 후 재시도하는지, 결과를 어떻게 검사하는지에 따라
실제 성공률이 달라진다.

OpenAI 공식 문서도 스킬을 `SKILL.md`와 선택적 scripts/references/assets를 가진 재사용 지침 폴더로
설명한다. 하네스는 스킬의 이름·설명을 먼저 보고 필요할 때 전체 지침을 읽는다. MCP나 도구가 실제
데이터와 행동을 제공한다면 스킬은 그것을 언제, 어떤 순서로 쓰고, 불완전 결과를 어떻게 처리할지
정한다. ([OpenAI Skills 개념](https://developers.openai.com/plugins/concepts/skills),
[OpenAI API Skills 가이드](https://developers.openai.com/api/docs/guides/tools-skills))

## 왜 하네스가 필요한가

LLM 단독 출력은 보통 “다음에 올 법한 텍스트”다. 개인 PC 제어에는 다음 문제가 추가된다.

1. 화면과 파일은 매 순간 바뀐다.
2. 클릭 한 번이 다른 창이나 다른 파일에 적용될 수 있다.
3. 성공처럼 보이는 메시지와 실제 성공은 다를 수 있다.
4. 삭제, 전송, 설치, 인증은 잘못되면 복구 비용이 크다.
5. 음성 명령에는 오인식, 배경 대화, 부정문, 인용문이 섞인다.

하네스는 이 문제를 모델의 “조심성”에만 맡기지 않는다. 입력을 typed schema로 제한하고, 실행 직전
대상과 권한을 다시 검사하며, 위험하면 사용자 승인을 받고, 실행 후 OS 상태를 독립적으로 읽는다.
따라서 하네스는 지능을 새로 학습시키는 장치라기보다 **모델의 능력이 실제 환경에서 결과로 이어지게
하는 제어 구조**다.

## 하네스에 따라 LLM 성능이 어떻게 달라지는가

모델 가중치를 고정해도 하네스가 바뀌면 다음 지표가 달라질 수 있다.

- **성공률**: 더 정확한 관찰과 도구 인터페이스가 잘못된 행동을 줄인다.
- **복구율**: 오류를 읽고 제한적으로 재계획하면 중간 실패에서 회복할 수 있다.
- **안전성**: 승인, allowlist, target binding, STOP이 위험 행동을 차단한다.
- **속도와 비용**: 불필요한 화면 캡처·모델 호출·재시도를 줄이면 토큰과 시간이 감소한다.
- **재현성**: 초기 상태와 verifier를 고정하면 같은 실험을 다시 측정할 수 있다.
- **사용자 부담**: 모든 행동을 묻지 않고 위험 행동만 묻도록 정책을 설계할 수 있다.

하지만 하네스가 복잡하다고 항상 좋은 것은 아니다. 잘못된 retry는 같은 실수를 반복하고, 긴 prompt는
비용과 혼란을 늘리며, 허술한 verifier는 실패를 성공으로 기록한다. 따라서 모델 이름만 비교하면 안 되고
**모델–하네스 조합**을 동일한 작업, 초기 상태, 예산, 평가기로 비교해야 한다.

`AI Agents That Matter`는 정확도만 보면 복잡하고 비싼 에이전트를 과대평가할 수 있으므로 정확도와
비용을 함께 최적화하고, 표준화된 재현 가능한 평가를 해야 한다고 지적한다.
([Kapoor et al., 2024](https://arxiv.org/abs/2407.01502))

## “추론 과정보다 결과가 중요하다”의 정확한 뜻

이 말은 “생각하지 말자”가 아니다. 다음처럼 해석해야 한다.

- 내부 추론은 행동을 고르고 위험을 피할 만큼 사용한다.
- 사용자에게 긴 사고 기록을 보여 주는 것을 성능으로 착각하지 않는다.
- 완료 판정은 설명이 아니라 최종 상태와 verifier 증거로 한다.
- 결과만 맞으면 된다는 이유로 안전, 권한, 개인정보를 무시하지 않는다.
- 논문에는 숨은 사고 문자열 대신 action, observation, 오류 code, latency, 승인, verifier 결과를 기록한다.

ReAct는 추론과 행동을 번갈아 사용해 계획을 갱신하고 외부 환경에서 새 정보를 얻는 방식이 reasoning-only
또는 acting-only 접근보다 유리할 수 있음을 보였다. 즉, 좋은 원칙은 “추론 제거”가 아니라
**추론을 관찰과 행동에 묶고 최종 결과로 평가하는 것**이다.
([Yao et al., 2022/ICLR 2023](https://arxiv.org/abs/2210.03629))

## 스킬이 개인 로컬 머신 제어를 효율적으로 만드는 이유

로컬 PC 작업에는 사용자별 경로, 앱, 보안 정책, 검증 방법이 반복된다. 스킬을 사용하면 매번 긴 prompt로
이를 다시 설명하지 않아도 된다.

1. **절차 재사용**: 관찰→실행→재관찰→검증 순서를 매 작업에 재사용한다.
2. **도구 선택 단축**: API/CLI/UIA/화면 클릭 중 더 안정적인 경로를 먼저 고른다.
3. **실수 감소**: 정확한 대상 확인, 복구 가능한 변경, secret 비노출 같은 규칙을 빠뜨리지 않는다.
4. **context 절약**: 이름과 짧은 설명만 먼저 보고 관련 작업일 때만 전체 스킬을 읽는다.
5. **일관된 완료 판정**: “명령이 성공했다”가 아니라 readback, test, hash, 화면 상태로 끝을 판단한다.
6. **개인화와 이식성**: 모델을 재학습하지 않고도 사용자의 작업 방식과 프로젝트 절차를 파일로 유지한다.

다만 스킬은 권한을 늘리지 않는다. “메일 보내는 법” 스킬이 있어도 사용자가 메일 전송을 허가한 것은
아니며, “PC 제어” 스킬이 있어도 마이크·카메라·생체인증 동의가 생기는 것은 아니다. 또한 스킬 파일은
도구 사용에 영향을 주므로 신뢰하지 않은 스킬을 그대로 설치하면 prompt injection이나 데이터 유출
위험이 있다. OpenAI 공식 가이드도 스킬을 검토해야 할 privileged instructions로 취급한다.

## 실제 선례와 논문

### 1. SWE-agent: 인터페이스가 같은 모델의 실전 능력을 바꾼다

SWE-agent는 에이전트가 저장소를 탐색하고 코드를 편집하고 테스트하기 쉬운 Agent–Computer Interface를
설계했다. 논문은 이 인터페이스 설계가 행동과 성능에 영향을 준다고 보고했으며, 당시 SWE-bench
pass@1 12.5%, HumanEvalFix 87.7%를 기록했다. 핵심은 모델만이 아니라 모델이 컴퓨터를 다루는
인터페이스도 성능의 일부라는 점이다.
([Yang et al., 2024](https://arxiv.org/abs/2405.15793))

### 2. Voyager: 성공한 행동을 스킬 라이브러리로 재사용한다

Voyager는 Minecraft에서 성공한 복합 행동을 실행 가능한 코드 스킬로 저장하고 새 작업에서 검색해
조합했다. 별도 모델 fine-tuning 없이 skill library, 환경 feedback, self-verification을 사용했고,
기존 방법보다 고유 아이템 3.3배, 이동 거리 2.3배, 주요 기술 단계 도달 속도 최대 15.3배를 보고했다.
이는 “한번 성공한 로컬 절차를 스킬로 저장해 다시 쓴다”는 직접적인 선례다.
([Wang et al., 2023](https://arxiv.org/abs/2305.16291))

### 3. OSWorld: 말이 아니라 실제 컴퓨터 최종 상태로 평가한다

OSWorld는 Windows, macOS, Ubuntu의 실제 앱을 포함한 369개 작업과 실행 기반 evaluator를 제공했다.
초기 논문에서 사람은 72.36%를 완료했지만 당시 최고 모델은 12.24%였다. 언어 능력이 좋아도 GUI
grounding과 실제 조작 지식이 없으면 결과가 나오지 않는다는 증거다.
([Xie et al., 2024](https://arxiv.org/abs/2404.07972))

### 4. Windows Agent Arena: Windows 전용 재현 가능한 시험장

Windows Agent Arena는 실제 Windows 앱과 브라우저를 사용하는 150개 이상의 작업을 만들고 병렬 평가를
지원했다. 초기 Navi agent 성공률은 19.5%, 비보조 인간은 74.5%였고, 클라우드 병렬화로 전체 평가를
약 20분까지 줄일 수 있다고 보고했다. JARVIS-PC의 snapshot VM과 exact-cell 평가가 같은 연구 계열에
놓인다.
([Bonatti et al., 2024](https://arxiv.org/abs/2409.08264))

### 5. AgentBoard: 최종 성공과 중간 진행을 함께 본다

AgentBoard는 성공/실패 하나만 기록하면 왜 실패했는지 알기 어렵다는 문제를 다루며, subgoal 기반
progress rate와 multi-turn trajectory 분석을 제공한다. JARVIS-PC에서도 최종 task success를 가장
중요하게 두되, 실패 원인을 찾기 위한 단계별 observation과 stable error code를 함께 보존할 근거가 된다.
([Ma et al., 2024](https://arxiv.org/abs/2401.13178))

## JARVIS-PC에 적용하면

JARVIS-PC에서 NIM 모델은 전체 시스템이 아니라 한 부품이다.

```text
사용자 명령
  → 로컬 Intent/STOP gate
  → 최소화된 Context + 관련 Skill
  → NIM typed Planner
  → Capability Registry + Policy + 승인
  → Windows Executor
  → 독립 Verifier
  → Audit + 고정된 결과 알림
```

이 구조에서는 모델이 위험한 action을 제안해도 policy가 차단할 수 있고, executor가 성공이라고 해도
verifier가 OS 상태를 확인하지 못하면 완료가 아니다. 스킬은 자주 쓰는 작업 절차를 제공하지만 실제
권한과 안전 경계는 Registry, Policy, Approval, Executor가 강제해야 한다.

이번에 만든 개인 Codex 스킬은 다음 위치에 있다.

```text
C:\Users\YongE\.codex\skills\outcome-driven-local-work\SKILL.md
```

이 스킬은 로컬 build, repair, configuration, automation, computer-control 작업에서 자동으로 고려된다.
핵심 규칙은 다음과 같다.

- 요청을 관찰 가능한 완료 조건으로 바꾼다.
- 가장 안정적인 인터페이스로 작은 변경을 수행한다.
- 실행 결과를 독립된 경로로 다시 확인한다.
- 검증된 사실, 추정, 미실행, 외부 차단을 구분한다.
- 긴 설명보다 결과와 증거를 먼저 보고한다.
- 스킬을 추가 권한으로 해석하지 않는다.

## 논문에서 검증할 수 있는 실험 설계

하네스 효과와 스킬 효과를 분리하려면 같은 모델, 같은 prompt budget, 같은 temperature, 같은 초기 VM
snapshot, 같은 작업과 evaluator를 사용한다.

| 조건 | 구성 |
|---|---|
| H0 | NIM 모델 + 최소 도구 호출만 제공 |
| H1 | H0 + typed action + policy + executor/verifier loop |
| H2 | H1 + task-specific skill retrieval |

각 조건에서 여러 seed와 정상/고장 조건을 반복하고 다음 순서로 평가한다.

1. 주 지표: 독립 verifier가 판정한 task success.
2. 안전 지표: 무승인 RED 실행, target mismatch, secret 노출, STOP 실패.
3. 효율 지표: wall-clock latency, 모델 호출 수, input/output token, 재시도, 사용자 승인 횟수.
4. 복구 지표: fault 발생 후 recoverable success.
5. 분석 지표: 어느 subgoal에서 실패했는지와 stable error code.

이 실험은 “모델이 더 똑똑해졌는가”가 아니라 **같은 모델이 하네스와 스킬 때문에 실제 작업을 더
정확하고 안전하고 싸게 끝냈는가**를 측정한다. H2가 성공률을 높이더라도 비용이나 확인 부담이 크게
늘면 무조건 우월하다고 결론 내리지 않는다.

## 가장 쉬운 최종 요약

- 하네스는 AI 로봇의 몸과 안전벨트다.
- 스킬은 로봇이 다시 꺼내 보는 작업 카드다.
- 좋은 하네스는 같은 AI 머리도 일을 더 잘 끝내게 할 수 있다.
- 좋은 스킬은 매번 처음부터 고민하는 시간을 줄인다.
